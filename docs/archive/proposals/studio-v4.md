# Climbio Studio v4：AI 做工作，人只做判斷（設計提案）

> 狀態：**已決定方向；第 1、2 階段已做**（工作紀錄、命令列、判斷收件匣、自架同步服務，見 [studio-work.md](../../studio-work.md)；決定見最後一節）。各階段上線前，現行規格仍以 [studio-design.md](../../studio-design.md)、[studio-crag.md](../../studio-crag.md)、[studio-wall.md](../../studio-wall.md) 為準。

## 一句話

Studio 是**給 AI 用最順手、給人只留判斷**的資料工作台：AI 代理用命令列把岩館牆面、3D 牆、舊路線書、天然岩場做到「只剩要人看的地方」；人打開 Studio 只看到一排判斷題，點完就能發佈。所有進度、決定、實驗都寫在共享的資料夾裡，任何新的代理讀了就能接著做。

## 為什麼要改

| 現況 | 問題 |
|---|---|
| 五條線各有入口：`studio/crag/`、`studio/wall/`、`studio/wall3d/`（掛在 `/lab/`）、轉換路線書、發佈 | 人要先知道去哪裡；3D 不算正式工作區 |
| 只有路線書有命令列（`tools/guidebook.mjs`），牆面、3D、天然路線的工作只能在畫面上點 | AI 代理做不了大部分的工作，只能請人點 |
| 問題清單各自一套：Crag 的 `report.js`、Wall 的「待確認」、3D 的「不是岩點」 | 人要學三種檢查方式；判斷結果沒有統一記下來 |
| 工作進度只在對話和 commit 裡 | 換一個代理就要重新摸索做到哪 |
| 研究成果只有 Hold Lab 一頁是給人看的，其他實驗結論只在文字紀錄 | 新實驗要自己寫一頁；人看不懂進度 |

## 三層結構

```
┌───────────── 人（Studio 畫面）────────────┐
│  判斷收件匣：一題一張卡，證據圖＋AI 建議＋選項  │
│  發佈：全部判斷完的才出現                    │
└──────────────▲──────────────────────────┘
               │ 讀 questions、寫 decisions
┌──────────────┴─────── 共享專案資料夾 ──────────┐
│  公開格式 v2 的檔案（就是成品）                  │
│  .studio/work/  任務、執行紀錄、問題、決定        │
└──────────────▲──────────────────────────┘
               │ 讀寫同一份
┌──────────────┴──── AI 工具層（命令列）─────────┐
│  node tools/studio.mjs <線> <動作>             │
│  呼叫跟畫面同一份模組（convert.js、report.js…） │
└─────────────────────────────────────────┘
```

原則：**畫面和命令列呼叫同一份程式**（延伸現在 `tools/guidebook.mjs` 與 `studio/crag/convert.js` 的做法）；**成品就是公開格式**，工作紀錄只多一個 `.studio/work/`，去掉就能發佈。

## 1. 共享的工作紀錄（`.studio/work/`）

每個專案資料夾多一個工作紀錄，代理和人都只透過它交接：

| 檔案 | 誰寫 | 內容 |
|---|---|---|
| `state.json` | 工具 | 每條線做到哪一步、還剩幾題、能不能發佈（由下面三份推出來，可重算） |
| `runs.jsonl` | 工具 | 每次執行一行：時間、代理名稱、動作、工具版本、輸入、改了哪些 id、數字結果 |
| `questions/<id>.json` | 工具 | 要人判斷的題目（格式見下） |
| `decisions.jsonl` | 人（或被授權的代理） | 每個判斷一行：題目 id、選了什麼、誰、何時；也是之後訓練與評估的正解 |
| `notes.md` | 代理 | 交接筆記：這次做了什麼、卡在哪、下一步（給下一個代理讀） |

**接手規則**：新代理只要跑 `node tools/studio.mjs status <專案>`，就拿到 `state.json`＋最後一段 `notes.md`＋待答題數，不用讀對話紀錄。

**判斷題的格式**（四條線共用）：

```json
{
  "id": "q-…", "line": "wall | wall3d | convert | crag | publish",
  "kind": "hold-missing | hold-outline | not-a-hold | route-wall | route-line | position | …",
  "target": ["節點 id"],
  "evidence": [{ "image": "<id>.jpg", "box": [x, y, w, h] }],
  "proposal": { "label": "AI 建議", "patch": { } },
  "options": ["accept", "reject", "edit"],
  "why": "AI 為什麼不確定（信心、兩個模型不一致…）"
}
```

`patch` 用現有 `tools/guidebook.mjs apply` 的格式延伸（`move`、`set`、`remove`、`position`，加上岩點的 `outline`、`retire`）。人選「接受」就是套用這個 patch；選「修改」才打開對應的編輯器。

## 2. AI 工具層（`tools/studio.mjs`）

一支命令列、每條線同一組動詞；全部可以在沒有伺服器、沒有畫面的環境跑（要像素的步驟用無畫面 Chromium 跑 Studio 本身，跟 `guidebook.mjs build` 一樣）。

| 動詞 | 做什麼 |
|---|---|
| `status` | 做到哪、剩幾題、下一步建議 |
| `run <步驟>` | 跑一個自動步驟（偵測、精修、轉換、描線、歸岩壁…），寫 `runs.jsonl`，不確定的寫成題目 |
| `ask` | 列出還沒答的題目（`--json` 給代理） |
| `apply <patch>` | 套用修正，不動其他 id |
| `validate` | 公開格式驗證＋發佈底線 |
| `publish` | 發佈（見第 4 節，要人授權） |

| 線 | 自動步驟（`run`） | 留給人的題目 |
|---|---|---|
| **岩館牆面**（現 `studio/wall/`） | 偵測、HoldKit 外框、SAM2 精修、同色分路線、可能重複 | 漏掉的岩點、外框兩個版本選一個、是不是岩點、合併 |
| **3D 牆**（現 `studio/wall3d/`、`crag3d`） | 重建、切地面／天花板、懸空物、岩點投影 | 這塊是不是牆、這顆是不是岩點、切線位置 |
| **舊路線書轉換**（現 `guidebook.mjs`） | 讀檔、大綱、建書、換原圖、描紅線 | `report.js` 的每一項：路線分到哪面岩壁、線描得對不對、缺的位置 |
| **天然路線管理**（現 `studio/crag/`） | 照片歸岩壁、GPS 推估、路線表合併、Topo 對位 | 推估的岩壁位置、照片屬於哪面、新舊資料衝突 |
| **發佈**（共用） | 驗證、差異、組包 | 敏感座標、要不要發佈這一版（來源與授權由使用者負責，工具不出題） |

## 3. 人的畫面：判斷收件匣

Studio 首頁從「選工作區」改成**判斷收件匣**：

- 上面是所有專案的待答題數（「明德 Spray Wall：12 題」「大邱田：3 題」）；點進去一題一張卡。
- 卡片：證據圖放大到該看的地方、AI 建議疊在上面、底下三個鈕（接受／不對／修改）；鍵盤 A／X／E，手機左右滑。
- 「修改」才進現有的編輯器（Wall 編輯器、Topo、地圖、3D），改完回到下一題。現有編輯器保留，只是不再是入口。
- 題目全部答完的專案才出現「發佈」。
- 判斷是唯一一定要人做的事；專案設定、跑步驟、組包都交給代理，畫面上仍保留按鈕給沒有代理的人（同一份程式）。

這把現在三套檢查（`report.js`、Wall 的待確認、3D 的不是岩點）收成一種，步驟列只剩「判斷」「發佈」兩頁加各自的編輯器。

## 4. 發佈

- 共用現有 `studio/publisher.js`、`studio/dataset-publish.js`，不改開放資料集格式。
- 新增：發佈前自動產生**這一版的報告**（第 5 節的格式），跟著資料一起放進資料集：做了哪些自動步驟、人判斷了幾題、跟上一版差多少。
- 代理可以準備好發佈，但按下發佈（公開、收不回）一律由人確認，或由人在 `decisions.jsonl` 寫一筆 `publish` 授權。

## 5. 研究與進度報告：Lab 報告框架

把 Hold Lab 那一頁（同一張牆、一步一步比、數字摘要）變成**所有實驗共用的版型**，新實驗只交資料、不寫網頁。

### 報告的資料（`report.json`）

```json
{
  "id": "hold-outline-sam2", "title": "外框精修：SAM2 比 HoldKit 準多少",
  "question": "一句話：這個實驗要回答什麼",
  "status": "running | done | adopted | dropped",
  "owner": "代理或人的名稱", "updated": "…",
  "stages": [{ "key": "holdkit", "label": "HoldKit", "where": "手機", "image": "…", "overlay": "…json" }],
  "metrics": [{ "name": "IoU 中位數", "unit": "", "values": { "holdkit": 0.71, "sam2": 0.84 }, "better": "higher" }],
  "conclusion": "一兩句結論（數字）",
  "next": ["下一步"],
  "data": { "dataset": "climbio/walls", "items": ["牆包 id"] }
}
```

- 版型固定：標題與問題 → 前後對照的圖（拉桿、標出問題）→ 階段卡片 → 數字表 → 結論與下一步。跟 Hold Lab 現在的畫面一樣，Hold Lab 本身改成這個框架的第一份報告。
- 一個通用頁面 `lab/report/#<id>` 讀 `report.json` 畫出來；`lab/` 首頁列所有報告（狀態、最後更新、一句結論）。
- 報告資料放開放資料集的 `research/<id>/`（Hold Lab 現在讀 `climbio/walls` 的 `research/hold-lab/` 就是這個模式）；實驗程式與原始數據照現行規則留在研究用的 repo，climbio 只放通用頁面與格式。
- **進度報告**用同一個版型：每個 Studio 專案的 `state.json`＋`runs.jsonl` 自動產生一份（「自動做了幾成、人判斷了幾題、還剩什麼」），不另外寫。

### 任何代理加一個新實驗

1. 在研究用的 repo 開實驗資料夾，跑程式產生 `report.json` 與圖。
2. `node tools/studio.mjs lab push <資料夾>`：驗證格式後放進開放資料集 `research/<id>/`。
3. `lab/` 自動出現新卡片；結論採用後把 `status` 改成 `adopted`，並把對應的自動步驟接進 `tools/studio.mjs run`。

## 分階段

| 階段 | 交付 | 驗收 |
|---|---|---|
| 1 工作紀錄＋命令列骨架 | `.studio/work/` 格式（[studio-work.md](../../studio-work.md)）、`tools/studio.mjs`，路線書轉換先接上（呼叫 `guidebook.mjs`） | 新代理只靠 `status` 接手一本轉換到一半的路線書 |
| 2 判斷收件匣＋自架同步 | 首頁收件匣、題目卡片；同步服務（`Backend.caps.studio`）與一鍵部署到自己 Firebase 的說明 | 一本路線書從轉換到可發佈，人只在 iPad 的收件匣操作；另一個 Firebase 專案照文件部署成功 |
| 3 岩館牆面接上 | Wall 的偵測、精修、待確認變成 `run` 與題目 | 明德 Spray Wall 由代理跑完，人只答題 |
| 4 Lab 報告框架 | `report.json` 格式、`lab/report/`、Hold Lab 改用框架 | 新增一份實驗只交資料就出現在 `/lab/` |
| 5 3D 與天然路線 | 3D 牆升為正式線、Crag 的歸岩壁／GPS 推估變成題目；發佈附報告 | 大砲岩 3D、一個天然岩場各走完一次 |

每一階段都能單獨上線，前一階段不依賴後一階段。

## 不做

- 不改公開格式 v2 與各 Kit 的公開 API；`.studio/` 本來就不進發佈。
- 不讓 AI 推測位置、路線、署名（現行規則不變）：這些只能來自原始資料或人的判斷。
- 不處理來源與授權：由使用者負責，寫在服務條款與發佈的聲明，工具不出題、不加檢查。
- 不做私人發佈；Studio 本身不做帳號系統，同步服務的存取用自架者自己發的金鑰（見「共享放哪裡」）。

## 共享放哪裡：每個人自架的同步服務

目標使用者不只維護者：每個岩友、岩館或岩場維護者都只有自己的 AI 代理，要能用最小的成本做完同樣的工作。

- **同步服務是開源後端的一部分**（雲端函式＋資料規則，放進 `Backend.caps` 的 `studio`），跟現有分享、發佈一樣照 [deploy.md](../../deploy.md) 部署。使用者的代理把它部署到**使用者自己的 Firebase 專案**，Studio 接自己的後端；climbio.app 的後端只放主網維護者自己的私人專案，不收別人的工作資料。
- **沒有後端時照樣能做**：工作紀錄就是專案資料夾裡的 `.studio/work/`，代理在本機用命令列，人用電腦版 Studio 開同一個資料夾。同步服務只是把同一份紀錄放到雲端，讓 iPad、手機答題，格式不變。
- **一筆一筆寫**：題目一題一份、判斷一筆一行，AI 產生題目和人答題同時進行也不會互相蓋掉；這是同步服務做得到、整份檔案同步（雲端硬碟、git）做不到的。
- **公開走開放資料集**：工作資料留在自己的後端；發佈（成品）、研究有結論要合回公開版時，資料才放進 Hugging Face 的開放資料集。

| # | 問題 | 決定 |

| 2 | 首頁 | 改成判斷收件匣，工作區卡片收進「新專案」 |
