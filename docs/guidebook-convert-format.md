# 路線書轉換：詳細操作與大綱格式參考

> 本頁保留檔案匯入方式、轉換問題排除、Markdown 大綱語法與命令列工具。第一次使用請先閱讀[路線書轉換介紹與入門指南](guidebook-convert.md)。

你的岩場已經有一份路線書（Google 文件、Word、網頁、PDF 都可以），這篇教你把它轉成 [Climbio 公開格式 v2](../format/README.md)：任何 App、岩場站都讀得到，紅點貓可以離線看 Topo、辨識照片裡的路線。

大部分工作是自動的：Climbio Studio 的「轉換路線書」直接讀 Word 或網頁的匯出檔，用規則認出區、岩壁、路線表格和照片，不用 AI。規則讀不懂的地方（例如一張表列了好幾面岩壁的路線），你可以自己改幾行，或複製給任何免費的 AI 聊天整理。

## 你需要

- 電腦版 Chrome 或 Edge 開啟 https://climbio.app/studio/ 。編輯資料存於本機，確認內容與授權後可直接公開發佈。
- 路線書和裡面照片的權利：你自己寫、自己拍的，或作者授權給你的。發佈的授權是 CC BY-SA 4.0，署名寫在大綱裡。

## 1. 匯出路線書

| 路線書在哪裡 | 怎麼匯出 |
|---|---|
| Google 文件 | 「檔案 → 下載 → 網頁（.html，壓縮）」或「Microsoft Word（.docx）」，兩種都有表格和照片 |
| Word | 直接用 .docx |
| 網頁 | 瀏覽器「另存網頁（完整）」，把 .html 和圖片資料夾一起選進來，或壓成一個 ZIP |
| 文字型 PDF | 直接選入 `.pdf`：解析文字、依字級推測標題及部分路線編號與難度；PDF 內的照片不會直接擷取，要另外存檔一起選入，並人工檢查辨識結果 |
| 掃描型 PDF、紙本、其他 | 目前沒有 OCR：先取得文字貼到轉換文字框，照片另存檔；必要時用 AI 整理（見第 3 步） |

規則看的是文件的**結構**。路線書這樣寫，幾乎不用改：

- 區、岩壁（石頭）用文件的**標題樣式**（Google 文件、Word 的「標題 1」「標題 2」），不是只把字放大或加粗。
- 每面岩壁的路線放在它標題底下的**表格**，第一列是欄名：名稱、難度、類型、bolt（快扣數）、長度、首攀、說明……（欄名寫法很自由，「需要快扣數（不含 top anchor）」「路線描述」也認得）。
- 照片放在它的岩壁標題底下；照片下面緊接一行短字當圖說。
- 交通、停車、警示、救援資訊放在最上層的標題（例如「【交通方式】」）底下，會收進岩場的交通與說明。

## 2. 轉換

1. Studio 首頁「轉換路線書」。
2. 「選路線書的檔案」選第 1 步的檔案（ZIP、.docx、文字型 .pdf 或 .html 加圖片）。文字框出現**大綱**，下面是預覽：會變成幾區、幾面岩壁、幾條路線、幾張照片，紅字是要修的地方。
3. 照提醒改大綱（格式見下面「大綱怎麼寫」），預覽會跟著更新。常見的：
   - 「N 條路線放在區底下、還沒分到岩壁」：原文一張表列了整區的路線。在表格加一欄「岩壁」寫岩壁名稱（岩壁照片上常標著路線，例如「3.挖鼻孔5.11C」，照它分；用「複製給 AI」時把這幾張照片一起附給 AI），或先建立，之後在 Studio 的路線表格把「未分配」的路線拖到岩壁。
   - 「找不到這些圖檔」：大綱裡的圖檔名稱對不到選進來的檔案，把圖一起選進來。
   - 「沒有設成標題，照前後的編號當成標題」：作者忘了設標題樣式的「15.沙漏石」這類段落，規則照前後的編號補成標題，看一下對不對。
4. 按「建立」：岩壁、路線、照片都放好，路線書照片上的紅線自動描成 Topo，依序配給這面岩壁的路線。

## 3. 規則讀不懂的時候：複製給 AI

按「複製給 AI」，剪貼簿裡是一段提示、規則讀到的問題和目前的大綱（還沒有大綱時，把路線書的文字貼進文字框再按）。貼到任何 AI 聊天（ChatGPT、Gemini、Claude 的免費版都可以），把它回的大綱整段貼回文字框，預覽沒有紅字就可以建立。提示要求 AI 只整理、不翻譯、不編造；建立前還是看一下數量對不對。

這段提示也可以用命令列印出來：`node tools/guidebook.mjs prompt`。

## 4. 建立之後，在 Studio 接著做

照步驟列：

- **區域名稱**：改名、合併、刪除岩壁。
- **區域圖**：照片有 GPS 時岩壁地圖自動長出來；沒有的話，用地圖左上的「示意圖」載入路線書裡手畫的配置圖，對準後照著拖牆線。
- **路線表格**：把「未分配」的路線拖到岩壁、排順序、補資料。
- **路線圖**：修自動描的線、補 bolt 與確保站（見 [studio-crag.md](studio-crag.md) 的「畫 Topo」）。
- **發佈**：公開放進 Climbio 的開放資料集（CC BY-SA 4.0），得到公開網址和分享網址。之後改了再發佈，網址不變、版本加一。

## 5. 之後補上原始照片

路線書裡的照片常是縮小、畫了紅線的版本。拿到原始照片（同一次快門、比較大的那張）時，在這本「匯入照片」選進來：跟已經畫好 Topo 的照片是同一張的（路線書的圖裁切、縮小過也認得），自動換掉，Topo 照對位搬到原圖上，順序和岩壁不變；原圖有 GPS 時岩壁地圖跟著更新。再發佈一次就好：網址不變，收過這本的紅點貓下次打開時自動更新（只下載改過的照片）。

怎麼認同一張：先用特徵點找出原圖裡對應的區域，對齊後逐像素比，同一面岩壁的連拍、換個位置拍的不會被當成同一張。認不出的原圖會變成新的照片，在畫 Topo 裡重畫或刪掉。還沒畫 Topo 的路線書照片匯入時不換：按「路線」→「從照片描路線」，拿它跟原圖相減，把筆跡描在乾淨的原圖上。

已經發佈、但不是在 Studio 做的 Guidebook 或岩場站，先用首頁的「匯入岩場站」貼上它的網址收進 Studio，之後一樣補原圖、發佈。

## 資料完整：發佈前逐項對（AI 代理照這張做）

一本 Guidebook 公開出去，紅點貓看到的就是這些欄位；少一項就是使用者看到的缺漏。發佈前逐項對原始資料，來源有、包裡沒有的是轉換漏掉，要修；來源本身沒有的照下一節回報。

| 項目 | 從哪裡來 | 怎麼確認 |
|---|---|---|
| 名稱 | 大綱第一行 `#` | 發佈題的標題 |
| 國家 | 大綱「國家：tw」或 `--country`（由來源或使用者提供，不推測） | 發佈題寫出國家；沒有發佈會停下；發佈後世界清單在那個國家底下 |
| 岩場位置 | 原文座標、照片拍攝位置、使用者給的 | `check`／`validate` 沒有 `no-position`；發佈題寫出位置 |
| 署名 | 大綱「署名：」（原作者；同一個人接著改不寫「改編」） | 發佈題寫出署名；發佈後讀 `/p/<id>/index.json` 的 `attribution` |
| 授權 | 大綱「授權：」，預設 CC-BY-SA-4.0（公開資料集一律這個） | `index.json` 的 `license` |
| 來源 | 大綱「來源：」原始路線書的 https 網址 | `index.json` 的 `source` |
| 交通、說明 | 大綱「交通：」「說明：」 | 岩場節點的 `props` |
| 區、岩壁、路線數 | 原文 | `report.json` 的 `count` 跟原文逐區對；發佈題寫出數量 |
| 難度 | 原文（認不出系統的照「難度系統：」） | 報告沒有 `grade` 類的問題 |
| 首攀、長度、bolt、說明 | 原文表格 | 抽幾條對原文；來源有、包裡沒有的修 |
| 照片與 Topo | 路線書的圖、作者的原圖 | `report.json` 的 `no-topo`、`stub` 逐條處理；有原圖就一起選進 `build` 換掉 |
| 原始檔 | 轉換時選的檔案、`outline.md` | 包裡有 `source/`（`convert.json`、`outline.md`），之後才能 `rerun` |
| 更新還是新的一本 | 公開清單上有沒有這本（同一本或同名；不列入世界的用版本查詢找同一本） | 有就接在最新的一版後面；一次刪很多 Studio 擋下要改名，發成新的一本 |
| 世界清單 | 發佈時伺服器重寫 | `publish` 印出「世界清單：已在「tw」底下」 |

## 回報缺漏：分清楚「來源沒有」和「轉換漏掉」

岩場資料本來就可能不完整，要確認的是匯入、轉換沒有遺漏。回報缺什麼（首攀、說明、長度、位置、路線圖等）之前，先拿來源資料逐欄比對：來源有、輸出沒有的才是轉換問題，要修；來源本身就沒有的，標明「來源沒有」與該找誰補（岩場的資料維護者），不寫成轉換缺漏、不自行補值。回報一律分開列這兩類，附上來源與輸出的筆數。改了轉換程式用 `npm run eval:convert` 比較固定測試組的數字（`tests/convert/`）。

## 岩場位置（天然岩場必填）

文字裡的座標會自動變成岩場位置（岩場節點的 `geo`）：格式「緯度, 經度」，小數至少 3 位。依序找：交通說明裡「入口」「停車」「登山口」附近的、交通說明裡的第一組、岩場說明、各岩壁說明裡的第一組；緯度超過 90 的不收。找不到時預覽會提醒，轉換對話框的「岩場位置」欄可以貼上；沒有位置不能發佈（照片有拍攝位置也算）。

## 大綱怎麼寫

大綱是一份 Markdown，自動轉出來的就是這個格式，也可以從頭手寫：

```markdown
# 內湖大邱田
來源：https://docs.google.com/document/d/…
署名：楊礎豪
授權：CC-BY-SA-4.0
交通：導航到「武濟宮｜五路財神廟」
滿了可停興善宮

## 上攀區
說明：步道北側的岩壁

### 懸岩區
朝向：南
![](images/image24.jpg)

| 編號 | 名稱 | 難度 | bolt | 說明 |
| --- | --- | --- | --- | --- |
| 1 | 喬溪<br>Chelsea | 5.12c | 3 | 經典外傾大動作路線。 |
| 8 | 萌萌裂隙 | 5.10b | 傳攀 | 0.1~3 號岩械。 |

## 抱石區
類型：抱石

### 第一抱石
![](images/image21.jpg)

| 名稱 | 難度 | 首攀 | 說明 |
| --- | --- | --- | --- |
| 歡迎光臨 | V3 | 楊礎豪 2025/5/14 | 起攀後直上 |
```

| 寫法 | 意思 |
|---|---|
| `# 名稱` | 岩場（一份大綱一個） |
| `## 名稱`、`### 名稱`… | 底下還有標題的是區，其他是岩壁或石頭；層數不限 |
| `國家：` | 只寫在岩場底下，**一定要寫**：兩個字母的國碼（ISO 3166-1，台灣是 `tw`；「台灣」「臺灣」也認得）。紅點貓的世界照國家分組，沒寫的會被放到最後的「其他」；國家由原始資料或使用者提供，不推測。沒寫的大綱 `check` 報 `no-country`，發佈也會擋下 |
| `來源：`、`署名：`、`授權：`、`難度系統：` | 只寫在岩場底下。來源是原始路線書的 https 網址（紅點貓的岩場頁右上有連結）；授權預設 CC-BY-SA-4.0；難度系統是認不出系統的難度用的（預設 yds） |
| `交通：`、`說明：` | 岩場、區、岩壁都可以寫；下一行不是新欄位就接在同一段 |
| `朝向：` | 岩壁面朝的方向：度數，或 N、NE、東南、朝南 |
| `排列：` | 路線表格照照片由右至左或由左至右列（由右至左、由左至右）；寫在岩場、區或岩壁，底下的岩壁照這個。轉換 Word、網頁時，文件裡「Right to left 右至左」這類一行短字自動變成這個欄位 |
| `類型：` | 底下路線的預設類型（運動、傳統、抱石、頂繩……） |
| 其他文字 | 這一層的說明 |
| 表格 | 路線。欄名跟 Studio 的「貼上路線」一樣（名稱、難度、類型、長度、繩距、bolt、說明、首攀、定線者、代號／編號、岩壁）；格子裡換行寫 `<br>`；名稱是「中文<br>English」就是中英兩種名稱 |
| 表格的「岩壁」欄 | 路線放進這一層底下同名的岩壁（沒有就開一面）；這一層就是區 |
| 路線表檔（`.csv`、`.tsv`，單獨選，或代理交給 Studio 首頁） | 檔名當岩場標題，整張表當這個岩場的路線表格（欄名同上；逗號、分號或 Tab 分隔，不是 UTF-8 就當 Big5）；有「岩壁」欄就分到各面岩壁 |
| `.geojson` 地圖檔（跟大綱一起選，或放在 ZIP 裡） | 岩壁地圖：GeoJSON FeatureCollection，座標 `[經度, 緯度]`。`LineString` 的 `properties.wall` 是岩壁名稱（大綱的標題）：牆底線，畫線方向決定面朝（岩壁在左手邊、面朝右手邊）；`properties.kind` 是 `trail`（步道）或 `route`（建議行進路線）；`Point` 的 `properties.name` 是地點（`kind` 例如 `place`、`parking`）。畫出來的線當成手動畫的，之後加照片也不重算；名稱對不到岩壁的會提醒 |
| `![圖說](檔名或 https 網址)` | 岩壁的照片；放在區或岩場底下的是區域圖（配置圖、全景）：掛在那個區或岩場上、沒有路線、不描線，紅點貓顯示在岩場頁的區域照片。一面岩壁有好幾張表時，每張表是它前面那張照片拍到的路線：描線只在這幾條裡配（照排列轉成由左到右），某張照片的線數對不上也不會影響後面的照片；照片拍到的路線比找到的線多時，會把共線的拆開、黃色接線也算進去再找一次；同一張照片後面的第二張以後的表，是這張照片上沒有畫線的路線（例如沿用別條路線的直上變化）；只有一張表時，照片的線照清單順序配給岩壁還沒畫線的路線 |

- 難度照原文：`5.11a` 是 YDS、`V3` 是 V、`6a`／`6A` 是法式／Font，`5.12d?`、`V6-7` 也收。
- 類型沒寫時：V、Font 難度是抱石，有 bolt 數是運動攀登；bolt 欄寫「傳攀」「傳攀＋2 bolt」的是傳統攀登（bolt 數照數字）。
- 檢查大綱（例如請 AI 代理或腳本產生時）：`node tools/guidebook.mjs check 大綱.md`，見下面的「命令列」。

## 範例：內湖大邱田

大邱田的 Google 文件加上作者的 57 張照片一起選，按「建立」：路線書 46 張圖裡 29 張自動換成原圖，都放在對的岩壁；剩下的 17 張是起攀點特寫和路線書才有的圖（翻身石、小樹石、沙漏石的 Topo 沒有原圖），28 張沒對到的照片沒有放進來。只用 Google 文件（[原始資料](https://docs.google.com/document/d/1K2PiA76lwXmpWKRZNgBkL5PeoVjs9kyY2sy4yyMBtoQ/edit)）下載成網頁 ZIP 後直接轉換：2 區、22 面岩壁和石頭、49 條路線、46 張照片，交通與警示收進岩場；13 張交通照片和 2 張配置圖不放進照片。抱石區每顆石頭一張表，路線和照片自動放好，建立時紅線自動描成 33 條路線的 Topo。要人工處理的只有兩件：上攀區 14 條路線在同一張表，拖到 6 面岩壁；手畫的配置圖用「示意圖」對到地圖上畫牆線。

## 原始檔與重跑

Studio 按「建立」時，把這次轉換的原始資料存進專案的 `source/`，發佈、匯出 ZIP 都一起帶（放在開放資料集 `crags/<id>/source/`），任何人都能拿來重跑：

| 檔案 | 內容 |
|---|---|
| `source/<檔名>` | 轉換時選的檔案（路線書、照片、區域圖），照原樣；檔名只留英數與 `. _ -`，原檔名記在 `convert.json` |
| `source/outline.md` | 按「建立」時的大綱（含手改的部分） |
| `source/fig-<…>` | 換成原圖的那張路線書圖（作者畫線的那張），對照頁用 |
| `source/convert.json` | 轉換紀錄（`format: climbio-convert/1`）：`files`（`path`、原檔名 `name`、`size`，照選的順序）、`outline`、`position`（自己填的岩場位置）、`counts`（各步驟的數字：`files`、`images` 讀檔；`areas`、`walls`、`routes` 大綱；`photos` 放進岩壁；`traced`、`stubs` 描線；`swapped` 換原圖）、`topos`（換成原圖的照片：`photo` 是照片的 `sha256`、`name`、`figure`、`H` 是路線書座標到原圖座標的 3×3 單應性，列優先） |

建立之後再加進來、換掉路線書圖的原圖，也會存進 `source/` 並記進 `files`。建立之後在 Studio 做的修改（拖路線、改線、分岩壁）在發佈的內容裡，不在 `source/`：重跑得到的是轉換本身的結果。

[轉換路線書](https://climbio.app/guides/convert/) 頁面讀 `crags.jsonl` 裡有 `source` 的岩場，自動列出，並用 `fig-*` 與 `H` 對照同一張照片轉換前後。

重跑（要 `npm ci` 與 `npx playwright install chromium`）：

```bash
hf download climbio/crags --repo-type dataset --include "crags/<id>/source/*" --local-dir crags
node tools/guidebook.mjs rerun crags/crags/<id> --out pack
```

## 命令列（AI 代理與腳本）

不用打開 Studio 畫面，也能完成整個轉換。`tools/guidebook.mjs` 跟 Studio 用同一份程式：讀檔是 `studio/crag/convert.js`、轉換是 `outline.js`、問題清單是 `report.js`（Studio 的轉換預覽顯示同一份）；要讀照片像素的步驟（換原圖、描紅線）在無畫面的 Chromium 裡跑 Studio 本身，結果跟在 Studio 按「建立」一樣。需要 Node.js 22 以上，`build` 另外要 `npm ci` 與 `npx playwright install chromium`。

| 指令 | 做什麼 |
|---|---|
| `node tools/guidebook.mjs read <路線書…> --out <資料夾>` | Word、PDF、網頁、ZIP、大綱 → 資料夾裡的 `outline.md`、圖檔（照原本的路徑）、`map.geojson`（有的話）、`report.json` |
| `node tools/guidebook.mjs check <outline.md> [--json] [--position 緯度,經度]` | 印出數量和問題清單；`--json` 印出報告本身 |
| `node tools/guidebook.mjs build <outline.md> [原圖…] --out <資料夾> [--position 緯度,經度]` | 建成一本：照片放進岩壁、換上一起給的原圖、描紅線、沒描出線的補記號；輸出公開格式 v2 的包（`index.json`、各畫面與圖層、照片、預覽圖）和 `report.json`，跟 Studio「匯出 ZIP」的內容一樣 |
| `node tools/guidebook.mjs rerun <資料夾> --out <資料夾>` | 用原始檔重跑：資料夾是 `source/`（或含 `source/` 的包）；照 `convert.json` 用原檔名選同樣的檔案、大綱換成 `outline.md`（沒有就用讀到的）、填同樣的位置，按建立，輸出跟 `build` 一樣（含新的 `source/`） |
| `node tools/guidebook.mjs apply <包資料夾> <patch.json>` | 局部修正：只改點名的節點，其他 id、其他檔案都不動；改完過格式驗證才寫入，並更新 `report.json` |
| `node tools/guidebook.mjs validate <包資料夾> [--json]` | 每份 JSON 過格式驗證，加上轉換的底線：有岩場位置、每條路線在照片上有線或記號 |
| `node tools/guidebook.mjs fetch <岩場站網址> --out <資料夾>` | 任何岩場站的 v2 出口收成資料夾裡的包（跟 Studio「匯入岩場站」同一份程式，含照片）和 `report.json`；之後跟自己建的包一樣用 `tools/studio.mjs` 出題、核准、發佈 |
| `node tools/guidebook.mjs publish <包資料夾> [--country 國碼] [--new-book] [--unlisted] [--position 緯度,經度] [--studio <網址>]` | `--unlisted` 不列入世界（世界清單沒有，只有拿到連結的人打得開；上一版不列入的不用再給）。國家每次都要（`--country` 或大綱的「國家：」）。已經發佈過的書（同一本或同名）自動接在它最新的一版後面發成下一版，世界裡不會多出一本同名的；一次刪很多（大改）Studio 會擋下，要改名發成新的一本。真的是另一本同名的岩場才加 `--new-book`。發佈完確認紅點貓的世界清單。發佈：**這一版要有人核准**（`tools/studio.mjs` 的「要不要公開發佈」人在對話裡答 ok；只能由人答，內容改了要重新核准）。在無畫面的 Chromium 開主網的 Studio（預設 climbio.app），帶同步金鑰（環境變數 `CLIMBIO_STUDIO_KEY`、`CLIMBIO_STUDIO_URL`）代替 App Check，收進這本（包裡的 `source/` 一起進專案、一起發佈）、按發佈，印出公開連結。來源沒有位置時用 `--position` 填岩場位置（由人提供，不推測） |
| `node tools/guidebook.mjs prompt` | 給 AI 的整理提示（跟「複製給 AI」同一段） |

結束碼：`0` 沒有 error（可能還有要看一眼的路線）、`1` 有 error（缺圖、沒有岩場位置、格式不合）、`2` 用法或 patch 寫錯。

**報告**（`report.json`）：

- `issues`：整本的問題，`level` 是 `error`（不修不能建立或發佈）或 `check`（要人看一眼），`code` 是 `outline`（大綱規則讀到的問題）、`missing-images`、`no-position`、`invalid`（格式驗證）。
- `routes`：每條路線的 `id`、`name`、`wall`、`status`（`ok` 或 `check`）、`reasons`（`unassigned` 還沒分到岩壁、`stub` 沒描出線只放了記號、`no-topo` 照片上沒有線也沒有記號），以及 `at`：這條路線來自大綱的第幾行、表格第幾列，方便對回原文。`at` 只在報告裡，不寫進公開格式。
- `check` 階段的路線 id 每次都是新的（還沒建書）；要改就直接改 `outline.md` 再跑一次。`build` 之後的 id 固定，用 `apply` 改。

**patch.json**：一個陣列，依序套用。Studio 畫面上人能改的（路線表格、區域圖、路線圖、照片歸岩壁），這裡都改得到：

```json
[
  { "op": "move", "routes": ["路線 id"], "to": "岩壁 id" },
  { "op": "set", "id": "節點 id", "name": "新名稱", "props": { "grade": { "yds": "5.10a" }, "description": null } },
  { "op": "set", "id": "岩壁 id", "parent": "區域 id" },
  { "op": "add", "type": "wall", "name": "西壁", "parent": "區域 id" },
  { "op": "add", "type": "route", "name": "新線", "parent": "岩壁 id", "props": { "grade": { "yds": "5.9" } } },
  { "op": "remove", "routes": ["路線 id"] },
  { "op": "remove", "nodes": ["岩壁或區域 id"] },
  { "op": "photo", "photos": ["照片 id"], "to": "岩壁 id" },
  { "op": "shape", "node": "岩壁 id", "geometry": { "type": "LineString", "coordinates": [[121.5149, 25.1347], [121.5151, 25.1347]] } },
  { "op": "shape", "trail": true, "geometry": { "type": "LineString", "coordinates": [[121.514, 25.134], [121.515, 25.135]] } },
  { "op": "line", "photo": "照片 id", "route": "路線 id", "points": [[120, 980], [150, 420], [170, 60]], "bolts": [[135, 760], [150, 420]] },
  { "op": "position", "lat": 25.13473, "lng": 121.51491 }
]
```

- `set`：`props` 逐欄合併，值寫 `null` 是刪掉那一欄；`parent` 換上層（岩壁移進區域，`null` 回最上層；不能是自己底下的）；路線的順序是 `props.order`。
- `add`：`type` 是 `route`、`wall`、`area`，要有名稱；不給 `id` 就產生一個，印出「新增 …」。
- `remove`：`routes` 連同圖層裡這條路線的線、bolt、確保站一起拿掉；`nodes` 也收岩壁、區域：底下的節點移到上一層，岩壁上還有照片時先用 `photo` 移走（不刪照片）。
- `photo`：照片換岩壁（照片畫面的 `props.node`）。
- `shape`：地圖畫面的形狀，經緯度 `[經度, 緯度]`：岩壁的牆線（`LineString`，畫線方向決定面朝：岩壁在左手邊、面朝右手邊）、岩石或區域（`Polygon`）；`geometry: null` 拿掉；`trail: true` 加一條步道。
- `line`：路線在照片上的線，照片像素、由下往上；照片還沒有圖層就開一個。有給 `bolts` 就換掉這條的 bolt（由下往上 B01、B02…）；`points: null` 拿掉這條的線和 bolt。線上的號碼照這條在岩壁裡的順序。岩場位置一律來自原始資料（原文的座標、照片的拍攝位置或作者提供的），不要推測。

**建議流程**：`read`（或自己整理成 `outline.md`）→ `check` 修到沒有 error → `build` → 把 `report.json` 裡 `check` 的路線交給作者確認，能從原文判斷的用 `apply` 修 → `validate`。做好的包（整個資料夾）在 Studio 首頁匯入，就能接著編輯與發佈。
